## 1. How the connection works

Flamingo Chat uses **WebSockets** for all communication. There is no REST API. Everything — user init, matchmaking, messaging, leaving — happens over a single persistent WebSocket connection.

**WebSocket endpoint:**
```
ws://localhost:8080/ws
```

In production this will be `wss://` (secure WebSocket over TLS).

**The connection flow at a glance:**
```
Frontend                          Backend
   |                                 |
   |--- open WebSocket ------------->|
   |--- send "init" event ---------->|  (immediately after connecting)
   |<-- receive "ready" event -------|  (backend confirms identity)
   |                                 |
   |  (now free to use the app)      |
   |                                 |
   |--- send "join_queue" ---------->|
   |<-- receive "queue_joined" ------|
   |<-- receive "match_found" -------|  (when paired with someone)
   |                                 |
   |--- send "send_message" -------->|
   |<-- receive "message_received" --|  (partner gets this)
   |                                 |
   |--- send "leave_chat" ---------->|
   |<-- partner gets "chat_ended" ---|
```

## 2. The event protocol

Every message sent and received is a JSON object with this shape:

```json
{
  "type": "event_name",
  "payload": { }
}
```

- `type` — a string identifying what the event is
- `payload` — an object with the data for that event. Can be `null` for events that carry no data.

**Sending an event** means serializing this JSON and calling `websocket.send()`.

**Receiving an event** means parsing the JSON from `websocket.onmessage` and switching on `type`.

## 3. Connection and initialization

### Step 1 — Open the WebSocket

```javascript
const socket = new WebSocket("ws://localhost:8080/ws")
```

### Step 2 — Send `init` immediately on open

The very first thing you must do after the connection opens is send an `init` event. The backend will not accept any other events until this is done.

```javascript
socket.onopen = () => {
  const storedUserID = localStorage.getItem("flamingo_user_id") ?? ""

  socket.send(JSON.stringify({
    type: "init",
    payload: { user_id: storedUserID }
  }))
}
```

**`user_id` rules:**
- If the user is new, send an empty string `""`
- If the user has connected before, send their stored ID
- If the ID is invalid or expired, the backend will generate a new one and send it back

### Step 3 — Wait for `ready`

The backend responds with a `ready` event containing the confirmed user ID.

```javascript
socket.onmessage = (event) => {
  const { type, payload } = JSON.parse(event.data)

  if (type === "ready") {
    // Store this — it's the user's permanent identity
    localStorage.setItem("flamingo_user_id", payload.user_id)
    console.log("Connected as:", payload.user_id)
    // Now you can show the UI and let the user join the queue
  }
}
```

**After receiving `ready`, the user is fully initialized and can use all features.**

## 4. User identity and storage

The backend identifies users by a short random hex ID (e.g. `a3f9c2b1e4d70c88`). This ID is:

- Generated by the backend, never by the frontend
- Persistent across sessions if the frontend stores and resends it
- Lost if the frontend clears storage (backend will create a new one)

**Recommended storage:** `localStorage` with the key `flamingo_user_id`.

There is no login, no password, no account. The user ID is the identity. Treat it like a session token.

## 5. Matchmaking (the queue)

### Joining the queue

Send `join_queue` with the user's gender and their preference.

```javascript
socket.send(JSON.stringify({
  type: "join_queue",
  payload: {
    gender: "male",        // "male" | "female"
    preference: "female"   // "male" | "female"
  }
}))
```

**Matching logic:** Two users are matched when user A's `gender` equals user B's `preference` AND user B's `gender` equals user A's `preference`. Both must be satisfied.

### Acknowledgement — `queue_joined`

The backend immediately confirms the user is in the queue:

```json
{
  "type": "queue_joined",
  "payload": null
}
```

Show a "searching..." or waiting state in your UI after this.

### Getting matched — `match_found`

When a compatible partner is found, both users receive this event:

```json
{
  "type": "match_found",
  "payload": {
    "chat_id": "96a3deba5771b2ce",
    "partner_id": "9ed54084d4f2be31"
  }
}
```

**Store `chat_id` — you need it for every message you send.**

`partner_id` is the other user's ID. You can use it to display their identifier if needed (e.g. "Chatting with #9ed54084").

## 6. Chat and messaging

### Sending a message

```javascript
socket.send(JSON.stringify({
  type: "send_message",
  payload: {
    chat_id: "96a3deba5771b2ce",   // from match_found
    content: "hello!"
  }
}))
```

There is no acknowledgement sent back to the sender. If you need optimistic UI (show your own message immediately), do it on the frontend before sending.

### Receiving a message

The **partner** receives a `message_received` event when you send a message:

```json
{
  "type": "message_received",
  "payload": {
    "chat_id": "96a3deba5771b2ce",
    "sender_id": "bd70833acafa9546",
    "content": "hello!",
    "message_type": "text"
  }
}
```

`message_type` is currently always `"text"`. A `"system"` type is reserved for future server-generated messages (e.g. "partner joined").

## 7. Leaving a chat

### Leaving (you initiate)

Send `leave_chat` with the current chat ID:

```javascript
socket.send(JSON.stringify({
  type: "leave_chat",
  payload: {
    chat_id: "96a3deba5771b2ce"
  }
}))
```

After sending this, consider the chat over on your end immediately. Clear the chat state and return the user to the idle/home screen.

### Partner left — `chat_ended`

When your partner leaves, you receive:

```json
{
  "type": "chat_ended",
  "payload": {
    "reason": "partner_left"
  }
}
```

Show a "Your partner has left" message and give the user the option to join the queue again.

**After either leaving or receiving `chat_ended`, both users are back to idle status and can join the queue again.**

## 8. Keeping the session alive (ping)

The backend has a 30-second inactivity timeout. If no event is received from the client in 30 seconds, the session is marked inactive and the user is removed from any queue or chat.

Send a `ping` event periodically to keep the session alive:

```javascript
setInterval(() => {
  if (socket.readyState === WebSocket.OPEN) {
    socket.send(JSON.stringify({
      type: "ping",
      payload: null
    }))
  }
}, 20000) // every 20 seconds — safely under the 30s timeout
```

There is no pong response from the server for app-level pings. The WebSocket connection itself also has a low-level ping/pong running automatically — the app-level ping is separate and keeps the user's server-side session alive.

## 9. Error handling

### Receiving an error event

If the backend encounters a problem with your event, it sends:

```json
{
  "type": "error",
  "payload": {
    "message": "description of what went wrong"
  }
}
```

Common error messages:
- `"invalid message format"` — your JSON is malformed
- `"not initialized — send init first"` — you sent an event before `init`
- `"invalid join_queue payload"` — missing or wrong fields in join_queue
- `"unknown event type"` — you sent an event type the server doesn't recognize

### WebSocket disconnection

Handle disconnection and reconnect:

```javascript
socket.onclose = () => {
  console.log("Disconnected. Attempting to reconnect...")
  // Wait a moment then re-run your connection setup
  setTimeout(connectToServer, 2000)
}

socket.onerror = (err) => {
  console.error("WebSocket error:", err)
}
```

On reconnect, go through the full init flow again — send `init` with the stored user ID and wait for `ready`.

## 10. Complete event reference

### Events you send (client → server)

| Event | When to send | Required payload fields |
|---|---|---|
| `init` | Immediately on WebSocket open | `user_id` (empty string if new) |
| `join_queue` | When user wants to find a chat partner | `gender`, `preference` |
| `send_message` | When user sends a chat message | `chat_id`, `content` |
| `ping` | Every ~20 seconds to stay alive | none (`null`) |
| `leave_chat` | When user wants to end the current chat | `chat_id` |

### Events you receive (server → client)

| Event | When you receive it | Key payload fields |
|---|---|---|
| `ready` | After sending `init` | `user_id` |
| `queue_joined` | After sending `join_queue` | none |
| `match_found` | When paired with a partner | `chat_id`, `partner_id` |
| `message_received` | When your partner sends a message | `chat_id`, `sender_id`, `content`, `message_type` |
| `chat_ended` | When your partner leaves the chat | `reason` |
| `error` | When something goes wrong | `message` |

## 11. Full client lifecycle example

A minimal but complete JavaScript client:

```javascript
class FlamingoClient {
  constructor(url) {
    this.url = url
    this.socket = null
    this.userID = localStorage.getItem("flamingo_user_id") ?? ""
    this.chatID = null
  }

  connect() {
    this.socket = new WebSocket(this.url)

    this.socket.onopen = () => {
      // Step 1: always init first
      this.send("init", { user_id: this.userID })

      // Step 2: keep session alive
      this.pingInterval = setInterval(() => {
        this.send("ping", null)
      }, 20000)
    }

    this.socket.onmessage = (event) => {
      const { type, payload } = JSON.parse(event.data)
      this.handleEvent(type, payload)
    }

    this.socket.onclose = () => {
      clearInterval(this.pingInterval)
      console.log("Disconnected")
    }

    this.socket.onerror = (err) => {
      console.error("WebSocket error", err)
    }
  }

  handleEvent(type, payload) {
    switch (type) {
      case "ready":
        this.userID = payload.user_id
        localStorage.setItem("flamingo_user_id", this.userID)
        console.log("Ready as:", this.userID)
        break

      case "queue_joined":
        console.log("In queue, searching for partner...")
        break

      case "match_found":
        this.chatID = payload.chat_id
        console.log("Matched! Chat:", this.chatID, "Partner:", payload.partner_id)
        break

      case "message_received":
        console.log("Message from", payload.sender_id, ":", payload.content)
        break

      case "chat_ended":
        console.log("Chat ended:", payload.reason)
        this.chatID = null
        break

      case "error":
        console.error("Server error:", payload.message)
        break
    }
  }

  joinQueue(gender, preference) {
    this.send("join_queue", { gender, preference })
  }

  sendMessage(content) {
    if (!this.chatID) return
    this.send("send_message", { chat_id: this.chatID, content })
  }

  leaveChat() {
    if (!this.chatID) return
    this.send("leave_chat", { chat_id: this.chatID })
    this.chatID = null
  }

  send(type, payload) {
    if (this.socket?.readyState === WebSocket.OPEN) {
      this.socket.send(JSON.stringify({ type, payload }))
    }
  }
}

// Usage
const client = new FlamingoClient("ws://localhost:8080/ws")
client.connect()
```

## 12. Notes for frontend design

**UI states to design for:**

1. **Idle** — user is connected but not in queue. Show a "Start chatting" button with gender/preference selectors.
2. **In queue** — searching animation. Show a cancel option.
3. **In chat** — message thread. Show partner ID (or anonymous label). Show "Next" / "Leave" button.
4. **Chat ended** — brief message that partner left. Option to search again or go idle.
5. **Disconnected** — show reconnecting state. Do not let user interact until `ready` is received again.

**Things the backend does not provide (frontend must handle):**
- Message timestamps — the backend stores them but does not send them in events. Add them on the frontend using `Date.now()` when a message is received or sent.
- Message history — there is no "load previous messages" endpoint. Each chat starts fresh. Only messages received during the current WebSocket session are available.
- Typing indicators — not implemented. Would require a new event type if added later.
- User display names — users are identified by their hex ID only. The frontend can label them "You" and "Stranger" or show a short version of the ID.

**CORS / Origin:** The backend currently allows all WebSocket origins. No special headers needed from the frontend.
