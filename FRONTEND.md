## 1. How the connection works

Flamingo Chat uses **WebSockets** for all communication. There is no REST API. Everything — user init, matchmaking, messaging, leaving — happens over a single persistent WebSocket connection.

**WebSocket endpoint:**
```
ws://localhost:8080/ws
```

In production this will be `wss://` (secure WebSocket over TLS).

**The connection flow at a glance:**
```
Frontend                          Backend
   |                                 |
   |--- open WebSocket ------------->|
   |--- send "init" event ---------->|  (immediately after connecting)
   |<-- receive "ready" event -------|  (backend confirms identity)
   |<-- receive "presence_update" ---|  (immediate snapshot of who's online)
   |                                 |
   |--- send "join_queue" ---------->|
   |<-- receive "queue_joined" ------|
   |<-- receive "match_found" -------|  (when paired with someone)
   |                                 |
   |--- send "send_message" -------->|
   |<-- receive "message_received" --|  (partner gets this)
   |                                 |
   |--- send "leave_chat" ---------->|
   |<-- partner gets "chat_ended" ---|
   |                                 |
   |<-- receive "presence_update" ---|  (every 5 seconds, automatically)
```

## 2. The event protocol

Every message sent and received is a JSON object with this shape:

```json
{
  "type": "event_name",
  "payload": { }
}
```

- `type` — a string identifying what the event is
- `payload` — an object with the data for that event. Can be `null` for events with no data.

**Sending an event** means serializing this JSON and calling `websocket.send()`.

**Receiving an event** means parsing the JSON from `websocket.onmessage` and switching on `type`.

## 3. Connection and initialization

### Step 1 — Open the WebSocket

```javascript
const socket = new WebSocket("ws://localhost:8080/ws")
```

### Step 2 — Send `init` immediately on open

The very first thing you must do after the connection opens is send an `init` event. The backend will not accept any other events until this is done.

```javascript
socket.onopen = () => {
  const storedUserID = localStorage.getItem("flamingo_user_id") ?? ""

  socket.send(JSON.stringify({
    type: "init",
    payload: { user_id: storedUserID }
  }))
}
```

**`user_id` rules:**
- New user → send empty string `""`
- Returning user → send their stored ID from localStorage
- If the ID is invalid or not found on the server, a new one is generated and sent back

### Step 3 — Wait for `ready`

The backend responds with a `ready` event:

```json
{
  "type": "ready",
  "payload": {
    "user_id": "a3f9c2b1e4d70c88"
  }
}
```

```javascript
case "ready":
  localStorage.setItem("flamingo_user_id", payload.user_id)
  // User is now initialized — show the UI
  break
```

### Step 4 — Receive immediate presence snapshot

Right after `ready`, the server sends a `presence_update` so the frontend immediately knows how many people are online, without waiting for the next scheduled broadcast.

**After receiving `ready`, the user is fully initialized and can use all features.**

## 4. User identity and persistence

The backend identifies users by a short random hex ID (e.g. `a3f9c2b1e4d70c88`). This ID is:

- Generated by the backend, never by the frontend
- Sent back in the `ready` event after init
- Persistent across page refreshes if stored in `localStorage`

**Recommended storage:** `localStorage` with key `flamingo_user_id`.

```javascript
// Save on ready
localStorage.setItem("flamingo_user_id", payload.user_id)

// Send on reconnect
const storedID = localStorage.getItem("flamingo_user_id") ?? ""
```

### Important limitations to know

**The user ID persists as long as:**
- The browser's localStorage is not cleared
- The server has not restarted

**The user ID is lost when:**
- The user clears their browser storage
- The server restarts (all state is in memory, not a database)

**There is no explicit expiry on the user ID itself.** The server will recognize a returning user ID indefinitely as long as the server has been running continuously. There is a session inactivity timeout of 30 seconds — but that only affects the session (connection state), not the user ID. If the user closes their tab and reopens it later, they reconnect with the same ID and get it back in the `ready` event.

**There is no 6 or 12 hour expiry** in the current backend. If you need time-based expiry, it would need to be added to the backend — either store a `CreatedAt` on the user and reject IDs older than N hours, or add a database so state survives server restarts.

For now: treat the user ID like a browser session — valid until the server restarts or the user clears storage.

## 5. Live presence counts

The server broadcasts online user counts to **all connected clients** every **5 seconds** automatically. You do not need to request this — just handle the event.

```json
{
  "type": "presence_update",
  "payload": {
    "total_online": 42,
    "male_online": 18,
    "female_online": 24
  }
}
```

```javascript
case "presence_update":
  updateOnlineCounter(payload.total_online, payload.male_online, payload.female_online)
  break
```

**Timing:** The first `presence_update` arrives immediately after `ready` (so the counter appears instantly). Subsequent updates arrive every 5 seconds. Display these counts live in your UI — they're a useful signal for users deciding whether to join the queue.

**Note:** Users who have not set their gender yet (brand new, haven't joined queue) are counted in `total_online` but not in `male_online` or `female_online`. So `male_online + female_online` may be less than `total_online`.

## 6. Matchmaking (the queue)

### Joining the queue

Send `join_queue` with the user's gender and their preference:

```javascript
socket.send(JSON.stringify({
  type: "join_queue",
  payload: {
    gender: "male",        // "male" | "female"
    preference: "female"   // "male" | "female"
  }
}))
```

**Matching logic:** Two users match when A's `gender` equals B's `preference` AND B's `gender` equals A's `preference`. Both conditions must be true simultaneously.

### Acknowledgement — `queue_joined`

```json
{ "type": "queue_joined", "payload": null }
```

Show a searching/waiting state in your UI after this.

### Getting matched — `match_found`

```json
{
  "type": "match_found",
  "payload": {
    "chat_id": "96a3deba5771b2ce",
    "partner_id": "9ed54084d4f2be31"
  }
}
```

**Store `chat_id`** — every message you send requires it. `partner_id` is the other user's ID, useful for display.

## 7. Chat and messaging

### Sending a message

```javascript
socket.send(JSON.stringify({
  type: "send_message",
  payload: {
    chat_id: "96a3deba5771b2ce",
    content: "hello!"
  }
}))
```

No acknowledgement is sent back to the sender. Add your own message to the UI optimistically before sending.

### Receiving a message

The partner receives:

```json
{
  "type": "message_received",
  "payload": {
    "chat_id": "96a3deba5771b2ce",
    "sender_id": "bd70833acafa9546",
    "content": "hello!",
    "message_type": "text"
  }
}
```

`message_type` is currently always `"text"`. `"system"` is reserved for future server-generated messages.

---

## 8. Leaving a chat

### You leave

```javascript
socket.send(JSON.stringify({
  type: "leave_chat",
  payload: { chat_id: "96a3deba5771b2ce" }
}))
```

Clear chat state on your side immediately after sending. Both users return to idle status and can join the queue again.

### Partner left — `chat_ended`

```json
{
  "type": "chat_ended",
  "payload": { "reason": "partner_left" }
}
```

Show a "your partner has left" notice and offer a "find new partner" button.

## 9. Keeping the session alive (ping)

The backend has a **30-second inactivity timeout** on sessions. Send a ping every 20 seconds:

```javascript
setInterval(() => {
  if (socket.readyState === WebSocket.OPEN) {
    socket.send(JSON.stringify({ type: "ping", payload: null }))
  }
}, 20000)
```

No response is sent back. The WebSocket itself also has automatic low-level ping/pong — the app-level ping is separate and keeps the server-side user session alive.

## 10. Error handling

### Error event

```json
{
  "type": "error",
  "payload": { "message": "description of what went wrong" }
}
```

Common messages:
- `"invalid message format"` — malformed JSON
- `"not initialized — send init first"` — event sent before init
- `"invalid join_queue payload"` — missing or wrong fields
- `"unknown event type"` — unrecognized event type

### Disconnection and reconnect

```javascript
socket.onclose = () => {
  clearInterval(pingInterval)
  setTimeout(connectToServer, 2000) // reconnect after 2 seconds
}
```

On reconnect, go through the full init flow again with the stored user ID.

## 11. Complete event reference

### Events you send (client → server)

| Event | When | Payload fields |
|---|---|---|
| `init` | Immediately on WebSocket open | `user_id` (empty string if new) |
| `join_queue` | User wants to find a partner | `gender`, `preference` |
| `send_message` | User sends a chat message | `chat_id`, `content` |
| `ping` | Every ~20 seconds | none (`null`) |
| `leave_chat` | User ends the current chat | `chat_id` |

### Events you receive (server → client)

| Event | When | Payload fields |
|---|---|---|
| `ready` | After `init` | `user_id` |
| `presence_update` | Immediately after `ready`, then every 5s | `total_online`, `male_online`, `female_online` |
| `queue_joined` | After `join_queue` | none |
| `match_found` | When paired with a partner | `chat_id`, `partner_id` |
| `message_received` | When partner sends a message | `chat_id`, `sender_id`, `content`, `message_type` |
| `chat_ended` | When partner leaves | `reason` |
| `error` | When something goes wrong | `message` |

## 12. Full client lifecycle example

```javascript
class FlamingoClient {
  constructor(url) {
    this.url = url
    this.socket = null
    this.userID = localStorage.getItem("flamingo_user_id") ?? ""
    this.chatID = null
    this.pingInterval = null
  }

  connect() {
    this.socket = new WebSocket(this.url)

    this.socket.onopen = () => {
      this.send("init", { user_id: this.userID })
      this.pingInterval = setInterval(() => this.send("ping", null), 20000)
    }

    this.socket.onmessage = (event) => {
      const { type, payload } = JSON.parse(event.data)
      this.handleEvent(type, payload)
    }

    this.socket.onclose = () => {
      clearInterval(this.pingInterval)
      setTimeout(() => this.connect(), 2000)
    }

    this.socket.onerror = (err) => console.error("WebSocket error", err)
  }

  handleEvent(type, payload) {
    switch (type) {
      case "ready":
        this.userID = payload.user_id
        localStorage.setItem("flamingo_user_id", this.userID)
        console.log("Ready as:", this.userID)
        break

      case "presence_update":
        console.log(`Online: ${payload.total_online} (${payload.male_online}M / ${payload.female_online}F)`)
        break

      case "queue_joined":
        console.log("In queue, searching...")
        break

      case "match_found":
        this.chatID = payload.chat_id
        console.log("Matched! Partner:", payload.partner_id)
        break

      case "message_received":
        console.log(`${payload.sender_id}: ${payload.content}`)
        break

      case "chat_ended":
        console.log("Chat ended:", payload.reason)
        this.chatID = null
        break

      case "error":
        console.error("Server error:", payload.message)
        break
    }
  }

  joinQueue(gender, preference) {
    this.send("join_queue", { gender, preference })
  }

  sendMessage(content) {
    if (!this.chatID) return
    this.send("send_message", { chat_id: this.chatID, content })
  }

  leaveChat() {
    if (!this.chatID) return
    this.send("leave_chat", { chat_id: this.chatID })
    this.chatID = null
  }

  send(type, payload) {
    if (this.socket?.readyState === WebSocket.OPEN) {
      this.socket.send(JSON.stringify({ type, payload }))
    }
  }
}

const client = new FlamingoClient("ws://localhost:8080/ws")
client.connect()
```

## 13. UI states to design for

| State | Trigger | What to show |
|---|---|---|
| **Connecting** | WebSocket opened, waiting for `ready` | Loading spinner |
| **Idle** | `ready` received | Gender/preference selectors + "Start" button. Show live presence counts. |
| **In queue** | `queue_joined` received | Searching animation. Show cancel option. |
| **In chat** | `match_found` received | Message thread. Partner label. "Leave" button. |
| **Chat ended** | `chat_ended` received | "Partner left" notice. "Find new partner" button. |
| **Disconnected** | `socket.onclose` fired | Reconnecting notice. Block all interaction until `ready` arrives again. |

**What the backend does NOT provide (frontend must handle):**

- **Message timestamps** — add them on the frontend with `Date.now()` when a message is sent or received
- **Message history** — there is no load-history endpoint. Each chat starts fresh. Only messages from the current session are available.
- **Typing indicators** — not implemented. Would need a new event type added to the backend.
- **User display names** — users are hex IDs only. Label them "You" and "Stranger" or show a short ID prefix.
- **Time-based user ID expiry** — the backend has no expiry on user IDs. They survive indefinitely while the server runs. If you want expiry, it must be added to the backend.
